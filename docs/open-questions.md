# 开工前必须摸清的问题

这些问题的答案决定架构，动手写 `client.js` 之前逐条用 `cordis_inspect_query` 查实（不要猜）。

## 1. 会话列表与「打开中的会话」由谁提供

左侧工作区列表、当前打开会话的集合，在 Web UI 里是哪个 Client Service / Store？调音台要展示的正是这份集合的子集。

## 2. 能否真正复用同一份会话运行时（真并排 vs 假并排）

关键问题：多个面板能否各自绑定一个会话，复用同一套消息流、输入框、工具审批卡片？

- **真并排**：每格都是完整会话视图，输入框可用、审批卡片可点。
- **假并排**：只能渲染只读的消息流快照 —— 那"每格独立输入框"这个核心诉求就不成立。

结论直接决定这个插件值不值得做下去。

## 3. 「等待决策 / 权限申请」在 Client 侧有没有可读信号

亮灯和告警的地基。需要找到：

- 审批 / 权限申请的产生与解决，是否发 Client 事件或落在某个 Store 字段；
- 会话状态里有没有"正在等待用户输入"这类可判定的态；
- 若信号只在 Host 侧，需要经由什么 Client Service 取到。

signal 不存在的话，第 2、3 层能力（亮灯、全局告警）都得重新设计。

## 4. 视图切换挂在哪

候选：

- Slot 装饰（在现有布局里插一个切换按钮）；
- 顶层整页视图替换（新形态接管主区域）；
- 新增顶层视图注册（与现有页面并列）。

取决于 Web UI 是否允许插件接管主区域，以及"常规 ⇄ 调音台"的切换要不要保住常规视图的状态。

## 5. 多会话并发订阅的风险

Web 端如果原本只有一个"活动会话"的概念，同时挂 N 个面板可能带来：

- 事件/流订阅互相干扰（A 格的消息串到 B 格）；
- 输入框快捷键、滚动位置、焦点抢夺；
- 性能：N 份渲染同时重绘。

需要确认会话运行时是否支持多实例绑定，以及有没有现成的多路复用方式。

## 6. 通道数量的上限与选择方式

一屏放几格？哪些会话进调音台（全部打开中的？手动 add？）？超出宽度后是滚动、换页还是缩小？——纯产品决策，但会影响布局实现（尤其是响应式与最小宽度）。
